# Fan Map 프로젝트 개발 계획 수립

## 역할

당신은 지도 기반 웹 서비스 구축 경험이 있는 시니어 프론트엔드 개발자이자 서비스 설계자입니다.

현재 저장소에는 다른 프로젝트에서 복사한 심플한 스타터 템플릿이 들어 있습니다.
스타터의 기술 구성과 재사용 가능한 공통 요소는 활용하되, 기존 화면 디자인과 페이지 구성은 따르지 않습니다.

이번 단계에서는 코드를 수정하지 말고, 현재 프로젝트를 분석한 뒤 실제 개발을 위한 구체적인 계획을 먼저 작성하세요.

---

# 1. 프로젝트 개요

## 프로젝트명

* 서비스명(가제): `Fan Map`
* Git 저장소명: `fan-map`

## 서비스 목적

스포츠 경기를 함께 관람할 수 있는 음식점과 술집을 지도에서 찾고, 이용자가 실제 관람 경험을 공유할 수 있는 지도 기반 서비스입니다.

야구에 한정하지 않고 다음과 같은 스포츠를 고려합니다.

* 야구
* 축구
* 농구
* 배구
* e스포츠
* 기타 단체 관람 수요가 있는 경기

## 핵심 가치

* 주변에서 스포츠를 볼 수 있는 장소 탐색
* 종목, 리그, 팀 또는 경기 기준 장소 확인
* 실제 이용자가 남긴 관람 정보와 후기 확인
* 관심 장소 저장
* 사용자 제보를 통한 장소 정보 축적

# 2. 참고 서비스

## 거지맵 참고 방향

거지맵의 지도 중심 사용 경험을 참고합니다.

참고할 요소:

* 첫 화면에서 지도를 크게 노출하는 구조
* 지도 위에 장소별 마커 표시
* 마커에서 핵심 정보를 빠르게 인지할 수 있는 구성
* 지도를 이동하거나 확대·축소하며 장소 탐색
* 지도와 장소 목록 또는 장소 정보 패널의 연계
* 사용자가 장소를 제보하거나 정보를 추가하는 흐름
* **제보 시 상호명 검색 → 네이버 검색 결과에서 실제 장소 선택** (주소·상호 자동 반영)
* 모바일에서 지도 탐색을 우선하는 인터페이스

그대로 복제하지 않을 요소:

* 거지맵의 브랜드, 색상, 캐릭터 및 시각 표현
* 가격 중심 서비스 구조
* 앱테크, 포인트, 출석, 광고 보상
* 핫딜 및 일반 커뮤니티
* 거지맵의 문구와 콘텐츠
* 화면을 그대로 따라 만든 UI
* 거지맵의 메뉴·가격·카테고리 체계

Fan Map의 목적과 콘텐츠에 맞게 새로 설계해야 합니다.

# 3. 제품 방향

## 서비스 성격

단순한 음식점 검색 서비스가 아니라 다음 성격을 갖는 서비스로 설계합니다.

> 스포츠 팬들이 실제로 경기를 관람한 장소와 관람 경험을 공유하는 참여형 지도

## 정보 신뢰 원칙

음식점이나 술집이 항상 스포츠 경기를 상영한다고 단정하지 않습니다.

다음처럼 사용자 경험에 기반한 표현을 사용합니다.

* 이 장소에서 경기를 봤어요
* 최근 관람 제보
* 관람 가능 여부는 방문 전 매장에 확인해 주세요
* 경기별 상영 여부는 달라질 수 있어요

매장이 공식 중계 장소라는 오해를 줄 수 있는 표현은 피합니다.

# 4. PoC 범위

이번 PoC에서는 핵심 사용 흐름 검증을 우선합니다.

## 필수 기능

### 4-1. 지도 탐색

* 지도 전체 화면 또는 지도 중심 레이아웃
* 현재 위치 확인
* 지도 확대 및 축소
* 지도 이동
* 현재 지도 영역의 장소 표시
* 장소 마커 선택
* 선택된 장소 강조
* 현재 지도 영역 재검색

### 4-2. 장소 정보

* 장소명
* 카테고리
* 주소
* 대표 이미지
* 스포츠 관람 제보 수
* 최근 관람 정보
* 관람 가능 종목
* 응원팀 또는 관련 팀
* 분위기 태그
* 사용자 후기
* 즐겨찾기 여부
* 지도 서비스의 원본 장소 정보로 이동

### 4-3. 검색과 필터

* 장소명 또는 지역 검색
* 스포츠 종목 필터
* 팀 필터
* 최근 관람 제보가 있는 장소 필터
* 즐겨찾기한 장소 필터
* 음식점 또는 술집 등 장소 유형 필터

PoC에서는 필터가 너무 복잡해지지 않도록 우선순위를 정해야 합니다.

### 4-4. 장소 제보

사용자가 임의로 장소명과 주소를 직접 생성하는 방식보다 **네이버 지역(Local) 검색 결과에서 실제 장소를 선택**하도록 설계합니다.

거지맵의 「상호명 검색 (네이버 결과 기준)」 흐름을 참고합니다.

기본 흐름:

1. 상호명 검색 (네이버 Local Search)
2. 검색 결과 목록에서 장소 선택 (도로명·지번 주소 확인)
3. 선택 장소로 이름·주소·좌표 반영
4. 스포츠 관람 경험 입력
5. 후기 및 태그 입력
6. 제보 등록

입력 후보:

* 관람한 스포츠 종목
* 리그 또는 대회
* 응원팀
* 관람한 날짜
* 관람한 경기
* 매장 분위기
* 화면 수 또는 시야
* 소리 제공 여부
* 단체 관람 적합 여부
* 간단 후기
* 사진

PoC에서는 모든 항목을 구현하지 말고 필수 입력과 선택 입력을 구분하세요.

### 4-5. 즐겨찾기

* 장소 즐겨찾기 등록 및 해제
* 즐겨찾기 장소 모아보기
* 비로그인 PoC에서는 로컬 저장 방식 검토
* 향후 로그인 및 서버 저장 구조로 확장 가능하도록 설계

# 6. 디자인 방향

## 전체 분위기

* 심플하고 현대적인 지도 서비스
* 스포츠 팬 서비스라는 인상
* 과도하게 남성적이거나 특정 종목에 치우치지 않는 디자인
* 지도와 장소 정보가 가장 잘 보이는 구성
* 장식보다 탐색성과 정보 위계 우선
* 모바일 웹에서도 앱처럼 자연스러운 사용성

## UI 원칙

* 지도 영역 최대 확보
* 마커 정보는 짧고 즉시 이해 가능하게 구성
* 필터는 선택 상태를 명확하게 표시
* 선택한 장소와 지도 마커를 서로 연동
* 장소 상세는 정보가 많아져도 단계적으로 펼쳐지는 구조
* 터치 영역은 모바일 사용성을 고려
* 로딩, 빈 결과, 위치 권한 거부, 오류 상태 포함
* 접근성 및 키보드 조작 고려

## 디자인 시스템

현재 스타터의 공통 UI나 스타일 체계를 먼저 확인하세요.

재사용할 수 있는 요소:

* 버튼
* 입력 필드
* 모달
* 드로어 또는 시트
* 카드
* 배지
* 탭
* 토스트
* 아이콘
* 테마 변수
* 반응형 유틸리티

기존 컴포넌트를 무조건 유지하지 말고, Fan Map에 적합한지 판단한 뒤 재사용·수정·제거로 구분하세요.

# 7. 지도 및 데이터 방향

## 지도 서비스

국내 PoC 기준으로 **네이버 지도**를 사용합니다.

구성:

* **네이버 지도 JavaScript API** — 지도 표시·마커·현위치·영역 이동
* **네이버 검색 > 지역(Local) API** — 제보 시 상호명 검색·장소 선택 (거지맵과 동일한 역할)

분석·구현 시 확인할 내용:

* 네이버 지도 JavaScript SDK 적용 방식 (`ncpClientId`)
* Local Search API 호출 방식 (서버 프록시, Client ID/Secret)
* 브라우저 환경변수 관리 (`NEXT_PUBLIC_` vs 서버 전용)
* 클라이언트와 서버 중 API 호출 위치
* Web 서비스 URL(localhost·배포 도메인) 등록
* 현재 위치 권한 처리
* 커스텀 마커와 오버레이
* 지도 영역 변경 이벤트
* 모바일 성능
* API 사용량 및 제한
* 네이버 장소 식별자 저장 가능 여부와 주의점

## 데이터 구분

### 지도·검색 API에서 가져올 기본 정보

* 장소 ID (가능 시)
* 장소명
* 주소 (도로명·지번)
* 좌표
* 전화번호
* 카테고리
* 원본 장소 링크 (네이버 지도 등)

### Fan Map에서 관리할 자체 정보

* 스포츠 관람 제보
* 종목
* 리그
* 팀
* 관람 날짜
* 경기 정보
* 분위기 태그
* 후기
* 사진
* 즐겨찾기
* 신고
* 등록자
* 생성 및 수정 일시

지도·검색 API의 장소 정보와 자체 사용자 데이터를 명확하게 분리하세요.

* 프레임워크와 버전
* 패키지 매니저
* 라우팅 방식
* TypeScript 설정
* 스타일링 방식
* UI 컴포넌트 체계
* 상태 관리
* 서버 상태 관리
* 폼과 유효성 검사
